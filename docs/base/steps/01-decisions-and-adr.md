# Шаг 01. Зафиксировать требования и архитектурные решения

## Цель

Устранить решения, которые нельзя безопасно угадать при проектировании БД, API, ролей, media storage и production topology. Результат этого шага — документация; прикладной код не пишется.

## Входные данные

- `docs/base/ProjectPlan.md`;
- контакты владельца продукта и ответственного за Dokploy;
- реальные требования к форме заявки, контенту и администраторам.

## Задачи исполнителя

1. Провести короткую сессию уточнения и заполнить `docs/ProductDecisions.md`:
   - production и staging domains;
   - поля заявки, обязательность, ограничения длины, согласие на обработку ПДн;
   - статусы и допустимые переходы заявки;
   - получатели уведомлений, CRM/webhook, допустимые вложения;
   - перечень управляемых страниц и блоков;
   - перечень параметров интеграций, их владелец и признак секретности;
   - роли администраторов и матрица разрешений;
   - SLA, ожидаемый трафик, пиковая частота заявок, максимальный upload;
   - срок хранения заявок, файлов и audit log;
   - local volume или S3-compatible storage на первом релизе.
2. Создать `docs/Architecture.md` с картой подтверждённых предметных областей. Не создавать пустые PHP-каталоги: описать только ответственность, владельца таблиц, публичные contracts и события.
3. Создать каталог `docs/adr/` и минимум четыре ADR:
   - `0001-ddd-layered-architecture.md`;
   - `0002-api-and-auth.md`;
   - `0003-deployment-topology.md`;
   - `0004-media-storage.md`.
4. Создать `docs/ApiContract.md` с базовыми соглашениями:
   - prefix `/api/v1`;
   - JSON error envelope;
   - ISO 8601 и семантика timezone;
   - pagination/filter conventions;
   - request/correlation ID;
   - выбранная защита публичной формы: rate limit, CSRF/auth model.
5. Зафиксировать спорные решения как `TBD` с владельцем и датой, но не оставлять `TBD`, блокирующие шаг 05: схема заявки и её статусы обязательны.

## Шаблон ADR

```md
# ADR-0001: DDD с разделением слоёв

- Статус: accepted
- Дата: YYYY-MM-DD
- Ответственные: ...

## Контекст
Почему решение требуется и какие ограничения известны.

## Решение
Выбранный вариант и точные границы применения.

## Альтернативы
Рассмотренные варианты и причины отказа.

## Последствия
Положительные эффекты, цена и условия пересмотра.
```

## Обязательная матрица ролей

В `docs/ProductDecisions.md` должна появиться таблица вида:

| Действие | super-admin | content-manager | lead-manager |
|---|---:|---:|---:|
| Управлять администраторами | да | нет | нет |
| Редактировать контент/media | да | да | нет |
| Просматривать/менять заявки | да | нет | да |
| Открывать Horizon | да | нет | по решению |

Названия ролей могут быть изменены, но доступ должен проверяться server-side, а не только скрытием элементов UI.

## Границы шага

- Не устанавливать пакеты и не создавать миграции.
- Не проектировать все будущие домены детально.
- Не выбирать Sanctum «на всякий случай»: он нужен только при подтверждённой browser auth или защищённом API.

## Проверка и приёмка

- Все четыре ADR имеют статус `accepted` либо явно указанное блокирующее решение.
- У формы заявки есть однозначная схема, validation rules и state transitions.
- Известны домены, storage backend, роли, retention и лимиты upload.
- `docs/Architecture.md` не разрешает `Domain -> Laravel/Eloquent/Filament`.
- Документы reviewed владельцем продукта и ответственным за инфраструктуру.

## Передача следующему исполнителю

Передать ссылки на принятые ADR, окончательную схему заявки, матрицу ролей, значения доменов и перечень переменных окружения без их секретных значений.
